## 1. What the layer is

`qemu-ohos-source/qemu-inprocess/` drives the QEMU system emulator as a library
inside the host process (VirtualWorld / HarmonyOS HAP):
`qemu_init()` → deferred autostart → `qemu_main_loop()` on a worker thread →
`qemu_system_shutdown_request()` → `qemu_cleanup()`.  There is no child
process, no PID, no `QProcess`; the C ABI (`qemu_inprocess.h`) exposes only a
session handle and frontend callbacks (display/input/audio/block).  No guest
image is embedded and none is booted by the harness.

Two mechanisms keep a fatal configuration error from terminating the host:

1. **Conversion** — direct `exit()`/`abort()` sites on the checked path record a
   structured failure and return (`QEMU_INIT_*`, `QEMU_INPROCESS_FATAL*`,
   `QEMU_INPROCESS_ABORT*` in `system/vl.c`, `util/qemu-config.c`,
   `system/physmem.c`, `tcg/region.c`);
2. **A structured fatal-error sink** (`include/system/inprocess-fatal.h`,
   `util/error.c`): while a checked init is armed, `error_fatal`/`error_abort`
   are captured and the caller returns.  When the trap is not armed every site
   keeps upstream semantics, so a standalone `qemu-system-aarch64` is
   unaffected.

`qemu_init_checked()` (in-process entry) never calls `exit()`/`abort()` for the
converted fatal paths, and uses no `setjmp`/`longjmp`.

## 3. Lifecycle implementation (why a real teardown is possible now)

`qemu_inprocess_cycle_teardown()` (`system/runstate.c`) is called from
`qemu_cleanup()` and from `qemu_init_checked()` after a failed init.  Upstream
never tears a machine down (it exits the process), so the in-process path had to
fix a chain of latent lifetime bugs, each root-caused with a stack:

1. vCPU threads are stopped, joined and taken out of service (`cpu_remove_sync`,
   `qdev_unrealize`) — they are not refcounted upstream;
2. machine memory wiring is released first (`machine_memory_cleanup`, every
   `MemoryRegion` disconnected from the process-lifetime containers), because a
   container holds a reference on the subregion's owner;
3. process-lifetime registries are retired (machine-init-done notifiers,
   resettable registrations, savevm handlers, ROM list, `-global` property
   registry, parsed options, migration state, signalfd compat thread);
4. devices are unrealized newest-first, GPIO output links released before
   unrealize, bus children freed synchronously during the teardown
   (`qdev_set_inprocess_teardown()`), RCU callbacks drained while the tree is
   still alive, then the machine is unparented/unref'd and the RCU queue drained
   again;
5. guest RAM stays mapped and is reused by the next cycle
   (`qemu_inprocess_keep_ram`), which removed the per-cycle re-fault cost.

The per-cycle heap leak (~605 KiB/cycle) was fixed in round 16 by attributing it
with an in-tree `malloc_logger` probe (`qemu-inprocess/alloc_trace.c`,
`VW_TRACE_ALLOC`): TB hash-table map, per-thread `TCGContext`, ARM cpreg arrays
and dynamic gdb features, pflash/fw_cfg buffers, per-init `AioContext` + GSource
and the compat signalfd thread/pipe were each released at teardown/init
(re)creation.  Measured residue is now ~4 KiB/cycle (bounded, listed in
`evidence/alloc-attribution-and-fixes.txt`).

## 4. The rare intermittent hang (round-16 open item): root cause and fix

**State.**  It only ever happened at the cleanup (and once during the following
init) of malformed-battery entry 8 (`-global no.such.prop=1`) — the only battery
entry upstream accepts (`warn_report` + continue) and therefore the only full
machine teardown in the battery phase.

**Mechanism (proven, full stack captured).**  Entry 8's command line has no
`-S`, so `autostart` is 1 and `qemu_init()` ends with
`qmp_cont -> vm_start -> resume_all_vcpus`: the vCPU threads start executing
guest/exception code *inside init*, and the harness (which never runs the main
loop for a battery entry) calls `qemu_cleanup()` directly.  `qemu_cleanup()`
upstream contract is a stopped VM, and its leading steps
(`migration_shutdown()`, block-export close, …) run before its own
`vm_shutdown()`; so the teardown ran concurrently with executing vCPUs.  The
captured hang (`evidence/hang-capture-stack-2026-10-17b.log`) shows the main
thread at `system/memory.c:1802  mr->destructor(mr);` with its PC inside QEMU's
TCG JIT code buffer — a corrupted/freed MemoryRegion destructor pointer was
called and execution ran away in JIT memory.  The same corrupted teardown state
produced the abort family captured under load
(`evidence/repro-entry8/`): `qemu_cond_destroy`/`qemu_mutex_destroy`
assertions, `qemu_sem_destroy` in `migration_instance_finalize`, a resettable
cycle assert (`s->count <= 50`) in the next init, and SIGSEGV.

**Reproduction.**  A dev-only all-thread stack dump on the watchdog timeout
(`VW_DUMP_STACKS`, Mach `task_threads`/`thread_get_state`/`backtrace`,
in-process, no child process) made the hang capturable; battery-attribution
switches `VW_BATTERY_ONLY`, `VW_BATTERY8_S` and `VW_BT_ON_CRASH` were added.
Under concurrent load (4 ASan battery loops + interleaved arms) the pre-fix
binary failed 26/900 runs (2.9 %), always at entry 8.  Without concurrent load:
0 failures in 700+ runs; ASan builds: 0 in 2 000 battery runs (addressed in
`evidence/rare-hang-root-cause-and-fix.txt`).

**Fix (API contract, no masking).**  An embedded core must not start executing
guest code inside init; the host decides when to run.  `qemu_init_checked()`
now defers the autostart (`qemu_inprocess_defer_autostart`), the
`qemu_init_internal()` autostart branch records
`qemu_inprocess_pending_autostart` instead of calling `qmp_cont()`, and
`qemu_inprocess_run()` starts the VM when the embedder asks
(`qmp_cont(NULL)`), then parks the vCPUs with `vm_shutdown()` before returning
so `qemu_cleanup()` always sees the stopped VM its contract requires.  The
standalone `qemu-system-aarch64` path is untouched.  Deterministic proof (dev
trace `VW_TRACE_AUTOSTART`): entry-8 init now returns
`runstate=prelaunch pending_start=1` (no guest execution), `-S` rounds as
before, and a new end-to-end test with 20 rounds **without** `-S`
(`VW_ROUNDS_NO_S`, init → deferred start in run() → stop → parked → cleanup)
passes.  Stress after the fix: 0 failures in the runs recorded in
`evidence/final-verification-summary.txt`.

## 5. `VW_ENABLE_QEMU_OHOS` build gate

`meson_options.txt` option `vw_enable_qemu_ohos` (boolean, **default false**).
Default build: stock QEMU targets only, the four spawn-owning sources compiled
exactly as upstream, no `qemu-inprocess-*` target (verified by
`nonohos_regression.sh`).  Option-enabled configuration: the four non-core
objects (`block/os-posix.c`, `migration/cpr-exec.c`, `net/tap.c`,
`semihosting/syscalls.c`) are not compiled and `ohos/vw_embedded_stubs.c` is
compiled into `libsystem.a`, so *every* executable of that configuration —
including the meson `qemu-inprocess-lifecycle-aarch64` — is spawn-symbol-free.
`build-qemu-inprocess/build_ohos_target.py` + `link_ohos_embedded.py` build the
archived shipped harness (`qemu-core-embedded-ohos`) independently with the
same object drop; both binaries are `nm`/`objdump`-clean
(`evidence/round17-nm-*.txt`).

## 7. Resource discipline

* ≤2 concurrent compiler processes, serial harness compile (`compile_harness_objs.py`);
* harness RSS ~46–60 MiB plain, ~145–150 MiB under ASan, far below the 1.5 GiB
  safety stop; the guest RAM (384 MiB block) is reused across cycles;
* no local LLM, no guest/UTM/VM started, `qemu-system-*` is never executed as a
  guest; the harness is a single process whose PID does not change;
* nothing committed/pushed; `qemu-source/**` stays pristine.

## 7a. Follow-up from the round-17 hypothesis tests (H1/H2/H3)

* H1 (vCPU/helper executing JIT code while the teardown frees memory) is
  disproved: the teardown phase trace shows vCPUs joined and out of the CPU list
  before the machine tree is retired; the captured hang PCs are outside the TCG
  code buffer (0x7000000000 + 0x3fffc000) and fall in PROT_NONE/rw- mappings;
  `threads_in_tcg=0` at every recorded phase.
* H2 (deferred-autostart inconsistency) is disproved: entry-8 init and cleanup
  both run `runstate=prelaunch` with the pending start cleared.
* H3 is hardened: `vw_rcu_quiesce()` drains the RCU queue to empty at the
  failed-init early-return path (which previously had no drain at all), before
  machine finalization and after it.
* The remaining failure is now captured precisely: inside
  `migration_incoming_state_release()`, the internal mutex of
  `postcopy_pause_sem_dst` is BUSY at destroy although all init flags are 1
  (`evidence/mig-sem-busy-mechanism.txt`, `evidence/mig-sem-busy/`).  The same
  capture also shows the failure only in the out-of-tree harness link built on
  the stale `qemu-build` directory (6/~1500 runs) and NOT in a consistent meson
  build of the same sources (0/1800 runs) -> harness-build consistency is the
  leading lead; the decisive next step is a fresh `qemu-build` directory from
  the pristine tree and a harness relink against it.

## 8. Remaining risks

1. **Open:** a rare load-induced race in the in-process machine teardown
   (captured stacks, §4 PART 2) is not root-caused.  It only occurs when the
   process is stressed by several concurrent ASan battery loops; the gate's
   normal acceptance runs are stable.  The verdict must therefore stay
   BLOCKED unless the gate scope excludes artificial concurrent stress.
2. The normal embedder path `init → run → stop → cleanup` relies on the run
   thread returning before cleanup (documented API contract); `run()` now parks
   the vCPUs before returning, so cleanup always starts from a stopped VM.
3. Host-SDK workaround: from-scratch macOS builds need upstream's
   `-Dpvg=disabled` on hosts whose SDK obsoleted `PGNewDeviceWithDescriptor`;
   unrelated to the OHOS work, but it must be carried into CI/other hosts.
